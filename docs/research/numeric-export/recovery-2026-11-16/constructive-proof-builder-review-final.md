# Constructive proof compiler: independent builder review

2026-11-17. Static design review only. Read the proposed design, PrismPM `AGENTS.md`, relevant normative `SPEC.md` boundaries, and the actual compiler/controller/Cargo/retained-reader entrypoints. No implementation, build, proof search, acceptance run, index or HEAD mutation was performed. References below are relative to `/workspace/scratch/prismpm-numeric`, except `draft`, which denotes the sibling game repository's `constructive-proof-design-draft.md`.

Two important decisions remain before a concrete implementation plan can meet the draft's guarantees.

## 1. High: the proposed verifier edit necessarily changes Released generation identities

**Question:** Will the candidate use a genuinely separate verification implementation/entrypoint that leaves the Released generator's existing source closure byte-identical, or will the amendment explicitly permit a reviewed change to Released generation identities and affected input locks? The draft currently requires the former outcome without providing a compatible integration boundary.

Draft lines 75–79 require the Engine façade at the fresh load in `verification.rs:2965`, while requiring Released/default generation recipes and ordinary identities to remain unchanged. But `controller/mod.rs:49–109` hashes the complete bytes of `verification.rs` into `library_generator_identity_for`, together with `library_build.rs`, `library_frontend.rs`, `lean_project.rs`, and exporter source/owner/custody files. Changing even the Engine import/load in that file changes the Released library generator digest. That digest contributes directly to library build IDs at `controller/mod.rs:1107–1116`.

The effect is wider than native libraries: `controller/mod.rs:735–747` supplies both generator digests for every computed input lock, and `input_lock.rs:58–69` unconditionally records both. Thus an ordinary application with a current `/3` SDK input lock can fail its next build on library-generator drift despite using the Released Engine and producing unchanged application code. This is a concrete incompatibility, not a hypothetical need to regenerate goldens.

The plan must identify an isolation boundary before editing those hashed files, or obtain the separately reviewed scope amendment already contemplated by draft line 79. Merely special-casing the old digest, excluding changed bytes from the existing recipe, or updating goldens would not preserve the actual existing generation contract.

## 2. High: choose a diagnostic Cargo workspace/package boundary that preserves ordinary source and packaged consumers

**Question:** Is the dual-Engine candidate built in a separately materialized diagnostic PrismPM workspace/manifest, or is the published `prismpm` package intended to acquire a new local compiler dependency? If the latter, what concrete distribution and bootstrap contract makes that dependency available to ordinary downstream Cargo consumers without making it an upstream release?

Draft lines 65–67 provide a fixed derived LexLean path and say it exists before Cargo resolution, but do not settle the production package boundary. The current workspace dependency is declared in `Cargo.toml`, consumed by `crates/prismpm/Cargo.toml`, and `xtask/Cargo.toml` itself depends on `prismpm`. Consequently an unconditional candidate dependency cannot be materialized by that xtask after it starts: Cargo must resolve it before building xtask. `scripts/vv.sh:216–224` enters through Cargo, and the first explicit metadata validation inside VV is only at `xtask/src/main.rs:902–909`. An external pre-Cargo materializer is a feasible implementation choice, but it must cover the initial invocation, not only a new audit stage.

More decisively, the ordinary package-API gate reconstructs a standalone PrismPM crate, then builds an offline downstream consumer (`xtask/src/main.rs:1616–1650`, `1734–1750`). `standalone_package_manifest` resolves inherited dependency tables and removes every `path`/`git` location (`1773–1847`). The resulting dependency would name the proposed unpublished `lexlean-constructive-diagnostic` version; the downstream manifest patches only the existing registered packages. A local target directory does not survive this publication boundary. Making the dependency optional alone does not eliminate Cargo's manifest/resolution requirement.

The separate diagnostic workspace approach appears compatible with the desired default isolation, but requires a concrete derivation/manifest/lock ownership contract for the candidate PrismPM build as well as the candidate LexLean tree. Alternatively the package admission/distribution scope must be expressly amended. This is not a reason to change any original dependency version or checksum, and publishing the diagnostic compiler is not implied authorization.

## Checked boundaries that do not need a further design decision

- **Proof recipes:** Both recipes symbolically suffice for the five unchanged propositions in `prism/numeric/src/Bounds.lex.tex`. Recipe B's strict scaling, whole-side equality transport and cancellation are constructive. A bounded normalizer can supply associativity/commutativity/zero/numeral equalities and transport the checked normalized conclusions to the source statement. Exact Init lemma names, bounded literal evaluation, malformed serialized certificate rejection, and measured caps remain implementation verification obligations, not reasons to request another abstract design. The current Bounds file still declares `[Quot.sound, propext]`; its theorem policies must be restored to empty for the new dispatch. Leaving them unchanged would deliberately select the base lowering under draft line 9.
- **Snapshot bridge:** `vendor/lexlean/src/artifact/snapshot.rs:16–25` is an owned, serializable DTO with the compiler semantics ID retained as data. Use its actual `canonical_bytes()` implementation at `:449–452` for the round-trip equality check; plain serde field-order serialization is not the canonical contract. The bridge can reject schema/round-trip differences. Build and verification results expose their necessary fields in `vendor/lexlean/src/api.rs:152–197`. Candidate diagnostics can map directly to Prism's public cause fields (`crates/prismpm/src/error.rs:216–276`), without constructing original compiler-private native details. None of these requires changing the original DTO schema.
- **Authority propagation:** The three Engine calls in the draft are not the complete propagation surface, but the missing plumbing is concrete: controller construction; `with_prepared_release` and `verify_release` (`controller/mod.rs:683–692`, `1277–1287`); `model_worker::Plan::load`, its equality/active scope and reload in `require_current_selection` (`controller/model_worker.rs:11–60`, `101–126`); nested `build_release_with_owner` and repeated `check_model_configuration` in `verification::run` (`verification.rs:2944–2989`); and generation/input-lock framing. `Plan::load` currently uses the original public `Project::load`; the plan must carry selected authority even if unchanged configuration parsing is deliberately shared. Library/application/system exclusion can be enforced after the existing projections at `controller/mod.rs:625–645`, before build emission. Separate diagnostic-fixture/browser Engine calls are outside this native-library candidate scope and need not be redirected.
- **LexLean attestation:** The existing `/2` attestation hashes the exact full build-manifest bytes at `vendor/lexlean/src/verify/mod.rs:2962–2971`; that manifest's output rows can bind the added certificate. Its compiler version/semantics and in-process executable hash are already emitted at `:2926–2940`. Adding a registered candidate fixed output does not, on this evidence, require a new attestation shape. Existing manifest/output-kind validators still need an explicit candidate-compatible certificate registration.
- **Acceptance and retained custody:** The current acceptance JSON does **not** point back to the verification manifest; the binding runs from `VerifyResult.attestation_id` to the manifest, then to acceptance and LexLean attestation (`library_verification.rs:381–478`). Retaining that complete externally selected result/manifest chain permits the acceptance payload to stay `/1`. Treating acceptance alone as proof-compiler acquisition evidence would be wrong. Current source-free readers already receive separate authority arguments, and verify that manifest digest and complete closed content (`scripts/library-sdk-check.mjs:214–245`; `scripts/library-owner-reader-replay.mjs:11–21`). Candidate `/4` dispatch must extend those explicit reader inputs with the frozen registered descriptor and retained measured producer authority, preserving installed-SDK versus source-bootstrap tagging. Existing `/3` key checks and `/3` frontend-owner checks must remain historical contracts, not silently reinterpret candidate records. This is substantial implementation work, but the draft specifies the necessary independent custody direction.

After the two ranked decisions, the remaining proof/checker, schema registration, strict authority threading and retained-evidence work is concrete enough to plan without another round of speculative questions. This review does not establish any generated proof, package build, SDK execution or acceptance result.

## Scoped disposition of revision 2

2026-11-17. Rechecked only the revised isolation/materialization decisions against the two findings above. No builds, proof searches or tests were run.

**Both original blockers are resolved at design level.** Revision 2 lines 61, 90, 98–100 and 138–159 place candidate Cargo manifests, the verifier, schema/readers and generator changes entirely in T_D; ordinary package manifests and production implementation remain untouched. Candidate source really receives a different generation identity (line 113), while ordinary `model/dependencies.toml` remains unchanged (line 140). The standalone materializer precedes derived Cargo (lines 73, 94, 144), whereas root xtask continues to resolve its unchanged ordinary dependencies. The ordinary package-API gate therefore no longer encounters the unpublished diagnostic dependency. The B → T_D → external D → outer R sequence also avoids the previously implicit self-hash cycles.

**One new, bounded materialization contradiction remains:** how does the exact complete base tree preserve its required package aliases under the regular-members-only extraction rule?

Revision 2 lines 65–73 bind the complete tracked base tree, then require extraction of only admitted regular members. The actual source workspace contains repository aliases including `crates/prismpm/model -> ../../model`, `schemas -> ../../schemas`, `stdlib -> ../../stdlib`, `vendor -> ../../vendor`, and `SPEC.md -> ../../SPEC.md` (observed with filesystem metadata, without reading or changing Git index/HEAD). These are operational inputs: `crates/prismpm/src/application_build.rs:25–30` includes package-relative model/stdlib/vendor/license files through them; `controller/mod.rs:1078` likewise includes the package-relative model dependency register. The existing complete tracked-source manifest explicitly recognizes symlink kind and hashes link-text bytes (`scripts/bootstrap-evidence.mjs:80–92`). This is therefore a real base-layout issue, not speculative adversarial input.

The controller must choose and register either narrowly enumerated, confined immutable base aliases with complete link/target custody, or a deterministic regular-file/path-rewrite materialization that maps the exact base aliases to the effective source tree before T_D is hashed. A regular-only extractor cannot silently omit the aliases and still reproduce the required workspace; blanket recursive dereferencing is not the stated exact-tree derivation and could create additional copies of restricted Lean/runtime trees. The choice must preserve the original four-file authority admission and leave the ordinary root untouched. No wider authority exception is needed or implied.

With that one extraction contract made explicit, the revision is clean to plan within this scoped review. This disposition establishes design readiness only, not implementation correctness or compiler/SDK admission.
