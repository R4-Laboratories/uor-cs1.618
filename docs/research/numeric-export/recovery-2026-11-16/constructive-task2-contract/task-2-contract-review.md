## Blocking corrections for Task2a

### B1 — Specify the actual lowered-declaration membership algorithm

Design line205 says to derive selected rows from semantic-module/2 declarations “in snapshot order,” including namespace lowering. That is insufficient for the actual producer and can select a different theorem set/order.

* Task1 `src/backend/constructive_nat/mod.rs:253` iterates `module.lowered_declarations()`, not raw `module.declarations`. `src/api.rs:275` iterates checked modules and passes **document.lean_module** as the certificate row's `module`.
* `src/ir/semantic.rs:2029–2036` deliberately skips `SemanticModule.elaboration` during serialization. `:3535–3540` flattens the elaborated declarations when present; it otherwise returns raw declarations.
* `src/artifact/snapshot.rs:276–328` retains changed/model elaborations separately in each summary declaration's `elaboration.declarations`; `:345` sorts those summary declarations by logical_id. That sorted summary is not source semantic declaration order. Raw semantic declarations remain available separately in `module.semantic.declarations`.

The brief must define the join: traverse modules in the producer's order, traverse semantic declarations in their original order, match each to the unique snapshot summary by logical_id, use its validated `elaboration.declarations` when present and the original declaration otherwise, then select empty-policy LinearArithmetic from that effective sequence. Bind module to `lean_module`, theorem to the effective declaration name, and source hash to the module source. Validate the raw/summary/linked_ir correspondence and reject missing, duplicate or inconsistent joins. Generated elaboration theorem/cross-check metadata is not automatically another selected LinearArithmetic declaration. Pin the exact policy and statement comparison.

Add fixture cases with source order differing from alphabetical order and with an elaborated declaration, alongside ordinary direct theorems. Alternatively explicitly scope a preliminary helper to direct-declaration fixtures and leave complete membership as an uncompleted gate; do not call that the complete independent certificate reader. This is required by adopted §7's complete selected-theorem membership, not a new proof algorithm.

### B3 — Finish the reader's byte-domain, anchor and resource interface

The rule interpreter itself is sufficiently concrete, but lines200–219 do not yet specify the complete callable boundary:

1. **Two canonical byte domains:** line16 correctly limits its no-final-LF convention to new Prism records. State the other domain explicitly in the JS helper: certificate, LexLean full manifest and snapshot use LexLean canonical **file** bytes with exactly one final LF. See Task1 `src/artifact/canonical_json.rs:1–6,49–54`, `src/artifact/snapshot.rs:449–458`, and `src/backend/constructive_nat/mod.rs` canonical writer. Raw certificate/manifest/snapshot file hashes include that LF; existing LexLean payload identity recipes must retain their existing no-LF distinctions. One universal Prism serializer would reject retained positives or hash different bytes. Pin cross-domain LF/escaping/UTF-8 vectors before implementation; these are not proposed changes to Task1.
2. **Independent snapshot/source binding:** the helper receives bytes and expected source/semantic IDs, but no expected snapshot/manifest hash or source-byte owner. IDs read from JSON cannot establish their payload's truth. The outer design does provide a projectExpectation owner; make the interface division explicit: either pass independently validated snapshot/manifest capabilities, or add their externally expected raw hashes and a bounded source-binding input. Specify where source hashes and module membership are recomputed. A plain HeldEvidenceOwner ensures safe access, not that caller-provided content is the expected snapshot. The helper's `{certificateSha256,rowCount}` remains component validation only.
3. **Shared budget:** define the fields/constructor/charging rules of sharedReaderBudget, numeric aggregate input cap, snapshot token/value cap, and manifest byte/value cap. Line219 caps certificate/snapshot individually and certificate tokens but gives no manifest cap or numeric aggregate bound. Include schema bytes/ref traversal in the bounded implementation plan; no unbounded recursive validator may evade the iterative/deadline rule. Define whether duplicate decoded keys, array/object members and primitive values consume each limit before allocation. The original `crates/prismpm/src/contracts.rs:1025–1035` item_count is not simply a count of JSON value tokens: it includes container member slots plus recursively counted values. `/4` must preserve that exact original total65536 convention, including embedded A/P additions, while any new counter convention is named separately.

These are wire/implementation-boundary choices, not requests to widen limits. Keep original smaller source/stage/process limits and the cumulative deadline. A fixture budget must not become a way to increase production authority limits.
