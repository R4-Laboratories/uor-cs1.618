# Constructive proof backport: bounded authority and design reconnaissance

2026-11-17. Design research only, based on `canonical-theorem-audit-diagnosis.md` and `canonical-theorem-source-feasibility.md`. No implementation, builds, proof searches, dependency/pin changes, or production-source edits were performed.

**Recommendation:** if the controller explicitly admits a new LexLean source authority, prefer a bounded constructive lowering of the existing authored `linear_arithmetic` form for a generic Nat-order fragment. Preserve the original compiler as the default authority and keep all original SDK/Lean/Rust/guest/exporter pins and empty-theorem policy. This is smaller than adding a general proof language, but it is **not compatible with pretending that the effective LexLean compiler and semantics identity are unchanged**. The existing lean4-prod backport authorization does not currently supply LexLean admission. Without an explicit plan/contract amendment covering that new authority, retain the blocker.

The five unchanged Bounds statements already have real empty-axiom Lean 4.32.1 witnesses. The source-only probe found specific missing hypothesis-introduction/composition paths, not global inexpressibility. Neither result warrants a theorem-policy exception.

## Actual boundaries that the design must cross

| Boundary | Current concrete entrypoint | Consequence |
| --- | --- | --- |
| Compiler dependency | Root `Cargo.toml:24,77`; `crates/prismpm/Cargo.toml:103` | PrismPM links the single vendored LexLean 0.4.0 crate. Changing a PATH executable alone cannot change its compiler. |
| Snapshot / model projection | `crates/prismpm/src/controller/mod.rs:569–592` (`Engine::load`, `snapshot`) | Selected authority must be established before the first source snapshot/model is accepted. |
| Generated build | `controller/mod.rs:840–864` (`prepared.engine.build`) | The same admitted compiler must produce the actual Lean and its manifest; post-generation Lean rewriting is not a repair. |
| Proof verification | `crates/prismpm/src/verification.rs:2957–2989` (`Engine::load`, `verify`) | Verification creates a new engine. A selection carried only by the earlier engine would be lost here. |
| Cross-phase identity | `verification.rs:3026–3045` | Source/semantic/build IDs and attested compiler semantics must equal the built model and manifest. All these bindings must remain enforced. |
| Library admission | `verification.rs:3140`; `library_verification.rs:76–173` | Full declaration and pinned runtime closure remains required, with empty source-theorem axioms. |
| Real SDK harness | Game `scripts/numeric/canonical/sdk-run.sh:55–58,76–97` | The harness builds a separate source PrismPM verifier but uses the original installed `lexlean lock/fmt` for preparation. A new semantics identity makes those stock-prepared locks stale for a candidate compiler. Preparation and linked Engine selection must agree. |

The existing source backport is specifically an **exporter** authority: `crates/prismpm/src/exporter/source.rs:5–65` closes selection over Released/NumericTask2c and their lean4-prod archives/descriptors; `SPEC.md:1848–1897` defines its exact acquisition contract. `Controller` currently stores only `exporter_source` (`controller/mod.rs:155–160`). `--exporter-source numeric-task2c` is not permission to replace LexLean, and its `/2` acquisition receipt cannot be reused as evidence for another compiler.

The LexLean API deliberately does not expose a caller-selected backend: `vendor/lexlean/src/api.rs:1–3,31–57` defines fixed Engine requests containing only selection. Adding an environment override, executable path, unchecked hook, or per-project raw tactic would violate that boundary. A new authority must be a closed, explicit source selection with genuine provenance, not an arbitrary backend setting disguised as a library option.

## Three options

| Option | Technical scope | Contract / identity impact | Assessment |
| --- | --- | --- | --- |
| 1. Constructive lowering of existing `linear_arithmetic` | In a separately admitted compiler, recognize a bounded generic fragment of Nat inequalities, implication hypotheses, addition, equality substitution and cancellation; construct ordinary proof terms using existing axiom-free Init lemmas. No new theorem names or source proof syntax. | New proof-lowering implementation and compiler identity. The original compiler's fixed lowering remains untouched. Affected source policies must genuinely become empty and all generated evidence must be regenerated. | **Smallest recommended route**, conditional on explicit new compiler admission. The five witnesses show this target is concrete; algorithm completeness/performance still need implementation tests. |
| 2. Small typed proof/certificate extension | Add checked introduction, local proof use/application, and closed Nat inference/certificate rules; extend source grammar/IR/checking/formatting/rendering. | In addition to compiler admission, requires normative source-language/schema/version compatibility design and new rejection surface. No raw Lean terms or arbitrary external theorem identifiers. | More expressive and potentially reusable, but larger than this repair and not justified as the first implementation merely because the existing helper probes failed. |
| 3. Wait for a correctly versioned upstream compiler | Preserve current failure until an upstream release provides an adequate constructive source path. | Current repository admits only the original 0.4.0 archive/revision. Even a genuine new release still needs dependency/provenance/source-authority admission and SDK/lock compatibility decisions; provenance alone does not override the fixed project pins. | Correct fallback if the plan cannot admit a separately identified backport. Waiting itself preserves all contracts; adopting a release is a separate governed change. |

For option 1, keep the algorithm generic over the checked semantic proposition and a bounded certificate/proof construction, never keyed to `Bounds`, theorem names, literal source hashes, or known output answers. The candidate may define constructive lowering for declarations requiring an empty audit while retaining historical lowering for other declarations, but that rule must be explicit and tested, not a hidden policy bypass. Unsupported or invalid empty-policy goals must fail closed; falling back to omega cannot silently satisfy an empty audit. The existing exact-nonempty executable policies and accepted historical compiler behavior must remain intact under their original authority.

The existing source syntax can remain compatible while proof generation changes. That does **not** establish byte compatibility, axiom-audit compatibility for every old exact policy, or compatibility with existing compiler locks/goldens. The work must specify and test its supported fragment, bounds and deterministic output. A narrow constructive lowering does not need a new handwritten Lean authority: the compiler emits proof terms as generated artifacts and original Lean checks them, as it does today.

## Required additive authority and identity design

1. **Retain the original base package unchanged.** `model/dependencies.toml:45–60` selects LexLean 0.4.0, revision `e0b74b81e6f49c83596a957d232c8383a5db1a25`, tree-manifest hash `dd35c1b0359c90c5896c5188c9e10bb4008883cb21ee92d35bc2fd4c8d4ac759`, crate hash `f2d579289052493d2c68274b10015d2cce544a78fbb876d73062184f09fb0a18`. Do not edit/reseal that tree or forge its package VCS record. Add a separate immutable compiler-source artifact/patch derivation and closed descriptor binding the original base, exact change set, resulting complete source identity, build recipe and actual candidate package identity. Preserve original Cargo dependencies where possible; any necessary additive Cargo resolution change must be explicit and reviewed.
2. **Admit the derivation, not merely a digest.** `xtask/src/audit.rs:372–448` requires the exact 0.4.0 package, selected revision, clean VCS provenance and registered tree/archive. `audit_lexlean_authority_archive` at line 451 independently compares complete archive membership and bytes. A candidate cannot satisfy this by writing a new manifest under the old identity. Add a separate, bounded admission path for the reviewed derivation while keeping the old path strict. If a derived package materializes original Lean authority files, prove those exact four files are unchanged copies of the originally admitted authorities; admit no fifth file, new tactic source, replacement runtime or handwritten project proof. If that cannot be represented without expanding the handwritten-authority set, reject this packaging route.
3. **Give the proof lowering an honest semantic identity.** LexLean `build.rs:24–29` embeds language/schema/golden data; `src/lib.rs:242–296` hashes those selected files. Rust implementation changes alone do **not** automatically change `compiler_semantics`. The existing versioned manifest `language/semantics-1.2.toml:7,15` records `lean_backend = "21"` and `proof_lowering = "3"`. The derived compiler must explicitly version/frame its changed lowering through its admitted normative semantics and descriptor; never manually force the old digest. Bind the actual implementation archive/tree and compiled verifier identity as well, since a semantics label alone is not source custody.
4. **Carry a single closed LexLean authority through the actual pipeline.** The snapshot, build and fresh verification engine must use it consistently; ordinary/application paths and omitted selection keep the original authority. A separately named native-library diagnostic candidate or a closed engine façade are implementation choices, but neither may label its changed engine as the installed SDK compiler. A library-only guard and the selection's presence in worker/build/generator identities are required. No caller URL/path, ambient PATH replacement, mutable workspace compiler, or fallback to a different authority. Since Engine runs in process, record the measured candidate verifier plus its admitted linked compiler source/build closure; do not invent a LexLean child-process receipt.
5. **Prepare and replay with coherent bindings.** `lexlean/src/lock.rs:1343–1365` refuses a stale compiler-semantics lock. The stock SDK `lexlean lock` cannot prepare the new compiler's lock while preserving a false original identity. Add an explicit admitted candidate preparation path, retaining and measuring the original SDK tools/inventory unchanged. Regenerate the actual LexLean locks, frozen source identities, snapshots, model/build IDs and attestations. Any new proof-compiler evidence needs a closed registered schema/admission rule and an independent retained authority at source-free replay. Do not add fields silently to closed historical manifests or reinterpret existing exporter receipts. Keep native frontend plans platform independent, with exact phase receipts; the original runtime registry stays authoritative if its bytes truly remain unchanged.

These are concrete additional admission requirements, not existing functionality. The original source-backport plan provides a precedent for separately identified sources, but the original native-frontend brief expressly preserved LexLean pins. Preserving the **base** pins while selecting an additional effective compiler is possible only after the plan explicitly permits that new authority, its dependency/build-identity changes, new semantics/locks, candidate preparation and receipt admission. If “preserve LexLean pins” means the effective compiler may never change, options 1 and 2 conflict and must remain blocked. This report does not quietly reinterpret that constraint or implement the amendment.

The unchanged native SDK OCI lock/inventory, original Lean 4.32.1, Rust/toolchains, guest contract, original exporter base pin and existing separately admitted NumericTask2c exporter are not obstacles to deriving proof terms, and must not be changed as collateral work. The new diagnostic compiler evidence must not qualify as an installed SDK release or replace source-independent SDK authority.

## Mandatory gates before claiming the repair

- Prove all five original Bounds statements from authored source, through the selected real compiler and original Lean/leanchecker, with **empty** observed axioms. Preserve statements, selected source closure and original arithmetic behavior. Remove their old exact pair only when genuinely empty proofs exist; retain acceptance and computational policies as appropriate.
- Test generic valid and invalid inference cases, variable/binder scope, strict/non-strict inequality and Nat subtraction traps, equality substitution, large literals, malformed/unbounded certificates, unsupported fragments and empty-policy failures. Require deterministic refusal within the original resource budget. No theorem-name special cases.
- Test admission mutations: candidate/base substitution, changed patch/tree/compiler, fake old semantics or package VCS, source selection loss between snapshot/build/verify, swapped preparation lock, and source-free replay without independent candidate authority. Retain the existing SDK inventory/launcher/actual-artifact and exporter custody controls.
- Run original compatibility/source audits and full VV, reviewed golden regeneration, complete source/runtime/erased-proof closure, both independent native exports, regeneration, original total 300-second stages, all four actual SDK build/verify/readers, std/no_std and corpus/golden gates. Original released/ordinary/application behavior must be demonstrated unchanged; local proof probes and an archive hash are not substitutes.

This focused comparison stops at the design boundary. Option 1 is the smallest proposed repair architecture; it still requires explicit additive LexLean admission and a plan amendment before implementation, while the current PP5003 blocker remains real.
